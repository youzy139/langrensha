# 多人同房对战 · 技术方案（讨论稿 v1）

> 状态：设计讨论稿，未动任何现有代码。
> 目标读者：维护者 + 参与讨论的朋友。
> 前提共识：狼人杀的本质是人与人的交互，单人机模式是"够用"，多人模式才是"好玩"。
> 从单人到多人不是加几个玩家，而是把"一条连接 = 一局游戏"的假设连根拔掉——这是质变。

---

## 1. 现状盘点：单人对局到底"单"在哪

现有 Web 模式的隐含假设链（也是多人化要逐层拆掉的）：

```
1 个浏览器标签页
 = 1 条 WebSocket 连接（/ws）
 = 1 个会话（_session_loop）
 = 1 局游戏（GameMaster）
 = 恰好 1 个人类玩家（WebHumanAgent）
```

具体耦合点（都已在代码中定位）：

| 耦合点 | 位置 | 单人体现 | 多人要改成 |
|---|---|---|---|
| 公屏信息流 | `WebLogger.print` → 唯一 `feed_q` | 全局只有一条消息队列，所有公开事件进同一条管道 | 房间级总线：公开事件扇出到 N 个人类客户端 |
| 私密信息 | `WebHumanAgent.note/wolf_hear` → 个人 `feed_q` | 天然按人隔离 ✅ | **可直接复用**，这是现有架构最大的资产 |
| 决策问答 | `_ask` → 个人 `inbox` 阻塞等待 | 人类不答，游戏永久卡住 | 加超时 + 托管策略（AFK 处理） |
| 会话生命周期 | `game_ws` → `_session_loop` | 连接断 = 游戏终止 | 连接断 ≠ 退出房间，要支持重连 |
| 角色分配 | `assign_human` 指定 1 人 | 一个 `human: true` | N 个人类座位 + AI 补位 |
| 赛后讨论 | `_handle_discuss` 单提问者 | 一个人问，AI 答 | 群聊：多个人类都能说，AI 参与 |

**好消息**：核心的 `GameMaster` 状态机、`PlayerAgent` 双层记忆、信息隔离纪律、
日志/复盘/回放体系**都不需要改**。人类和 AI 在引擎眼里本来就都是 `PlayerAgent` 子类，
多人化本质上是"把 WebHumanAgent 从一个变成 N 个，再给它套一个房间壳"。

## 2. 目标与边界

### 做（MVP 必须有）

1. **房间制**：房主创建房间 → 生成 4 位房间码 → 朋友凭码加入（局域网直接连房主 IP）
2. **大厅**：实时显示谁进了房间、选局型（6/8 人）、人类不足时 AI 自动补位
3. **多人类对局**：每个人类独立收到自己的身份/私密信息/狼人频道，公屏信息共享
4. **AFK 托管**：人类决策超时（默认 60s）→ 由 AI 兜底代答，游戏永不断流
5. **终局**：复用现有复盘 + 赛后讨论（升级为多人群聊）

### 不做（明确划出范围，防止工程爆炸）

- ❌ 账号系统/注册登录（房间码 + 昵称足够，局域网场景没有持久身份需求）
- ❌ 公网部署/匹配系统（MVP 只保证局域网；公网靠内网穿透工具，见 §6）
- ❌ 实时语音通话（那是腾讯会议的事；保留现有语音转文字输入即可）
- ❌ 移动端适配重构（现有页面手机浏览器能用就行）
- ❌ 反作弊强化（朋友局信任假设；服务端本来就只做最小投递，信息隔离天然成立）

## 3. 核心架构：房间模型

### 3.1 新的对象层级

```
Server (FastAPI 进程)
 └── RoomManager                    # 全局房间注册表：room_code → Room
      └── Room                      # 一个房间 = 一个生命周期容器
           ├── seats: [Seat]        # 8 个座位，每个座位 = 人类连接 或 AI
           ├── connections          # player_name → HumanConnection（feed_q + inbox + ws 引用）
           ├── gm: GameMaster       # 对局进行中才有；打完销毁，房间保留
           └── state: LOBBY / PLAYING / ENDED
```

关键决策：**房间和对局解耦**。对局结束房间不销毁，直接回大厅状态再开下一局——
这正是现在"再来一局"的多人版。

### 3.2 HumanConnection：把现在的"会话内脏"抽出来

现在 `feed_q`/`inbox` 是 `_play_one_game` 的局部变量，绑死一条 WS。
抽成一等公民：

```python
class HumanConnection:
    name: str                    # 座位名（Alice…）还是玩家自取昵称，见 §5 决策点 2
    feed_q: asyncio.Queue        # 服务端 → 这个人
    inbox: asyncio.Queue         # 这个人 → 服务端
    ws: WebSocket | None         # 断线时置 None，重连后挂回来
    status: ONLINE / AFK / DISCONNECTED
```

每个连接一个独立的 pump 协程（现有 `pump_out`/`pump_in` 的直接推广）。

### 3.3 消息路由：三种通道，泾渭分明

```
GameMaster 事件
 ├── 公开（logger.print）        → Room 总线 → 扇出到所有 HumanConnection.feed_q
 ├── 私密（agent.note）          → 该玩家的 feed_q            （现有代码已正确）
 └── 狼人频道（agent.wolf_hear） → 狼队友各自的 feed_q        （现有代码已正确）
```

改造量集中在第一点：`WebLogger.print` 从"push 到唯一队列"改为
"回调 Room.broadcast_public(line)"，Room 遍历扇出。
AI 玩家的 `hear()` 路径完全不动。

### 3.4 夜晚阶段的并发拷问（多人化最容易踩的坑）

现有夜晚流程对单人类是安全的，多人类要逐环节过一遍：

| 环节 | 现状 | 多人类时的问题 | 方案 |
|---|---|---|---|
| 狼人讨论 | 串行：一只狼说完下一只 | 两只人类狼排队说话，能忍（本来就是轮麦） | 保持串行，但每条消息实时扇出（已有 `wolf_hear`） |
| 狼人刀人投票 | `asyncio.gather` 并行 | 两只人类狼同时被问，各自 inbox 独立 ✅ | 直接可用 |
| 预言家验人 | 单独 await | 人类预言家 + 人类女巫同时被问？ | 现状串行：先狼后验再药，人类依次被问。MVP 接受串行 |
| 女巫用药 | 单独 await，两步问答 | 同上 | 同上 |
| 白天发言 | 严格串行 | 本来就是依次发言 ✅ | 不动 |
| 白天投票 | gather 并行 | 多个人类同时收到投票问句 ✅ | 直接可用 |

结论：**游戏流程代码几乎不用改**，并发结构天然兼容。真正的新工作是
`_ask` 的超时托管（§4.2）和断线处理（§4.3）。

## 4. 三个必须想清楚的体验问题

### 4.1 决策超时与 AFK 托管（优先级最高的新逻辑）

单人局人类挂机 = 游戏暂停，无所谓。多人局一个人挂机 = 七个人干等，**致命**。

方案：`_ask` 加 `asyncio.wait_for(inbox.get(), timeout=60)`：

- 超时 → 该座位进入 AFK 状态，公屏提示"X 思考超时，本轮由系统托管"
- 托管行为：发言 → "（X 暂时离开，过）"；投票/刀人/验人 → **调用该座位角色的 AI 临时代答**
  （复用 `PlayerAgent` 对应方法，AI 拿着人类的私有记忆做决策——记忆就在座位对象里，天然可行）
- 人类回来 → 任意操作自动解除 AFK，下一轮恢复手动

这个"AI 代打"机制本身是项目叙事的一个亮点：人机同构架构的副产品。

### 4.2 断线与重连

- 连接断开：座位标 DISCONNECTED，行为同 AFK（AI 托管），游戏继续
- 重连：客户端持有 `room_code + player_token`（加入房间时服务端签发的随机串，
  存在浏览器 localStorage），重连后走 `rejoin` 消息恢复座位
- 恢复内容：身份卡 + 自己的私密信息（从座位 agent 的 `private_notes` 重放）+ 公屏近期记录
- MVP 简化：重连只恢复"从现在开始的参与权" + 身份与私密信息，公屏历史给一份文本回放，
  不做逐条状态重建

### 4.3 人类之间的发言秩序

白天发言本来串行，天然没问题。狼人频道两只人类狼轮流发言，
加上"两轮自由麦"已有纪律，直接沿用。

唯一新增：**赛后讨论变群聊**——任何人都能随时发言，AI 对所有人类提问做
"点名匹配"（现有逻辑推广：问题里没点名任何 AI 但有其他人类发言时，AI 不抢话，
只在被点名或明确问全场时回应）。

## 5. 协议与页面变化

### 5.1 WebSocket 消息（新增，现有消息全部保留）

```jsonc
// 客户端 → 服务端
{"t": "create_room", "nickname": "阿泽"}                     // → 返回 room_code + player_token
{"t": "join_room", "room": "4F2K", "nickname": "小明"}
{"t": "rejoin", "room": "4F2K", "token": "..."}            // 断线重连
{"t": "set_config", "config": "8p"}                         // 仅房主
{"t": "start"}                                              // 仅房主；人类不足自动 AI 补位
{"t": "leave_room"}

// 服务端 → 客户端（新增）
{"t": "room_state", "players": [...], "host": "...", "config": "8p"}  // 大厅广播，有人进出就推
{"t": "joined", "name": "Alice", "token": "..."}            // 你的座位与凭据
{"t": "player_afk", "name": "Bob", "afk": true}
```

对局内消息（feed/ask/role/dead/game_over/review/discuss…）**协议不变**，
只是从"发给唯一连接"变成"按路由发给对应连接"——前端对局页零改动，工作量集中在大厅页。

### 5.2 前端

- 新增**房间大厅页**：创建/加入房间、玩家列表（谁是房主、谁是 AI 补位）、局型选择（仅房主可点）、开始按钮（仅房主）
- 现有对局页、终局面板、讨论区全部复用
- 加两个小元素：玩家列表的 AFK 标记、"系统托管中"提示样式

### 5.3 角色分配

`assign_human` 推广为 `assign_humans(config, human_names)`：
人类座位数 = 实际加入人数（不足局型人数由 AI 补位），角色照常随机洗牌，
人类是否可指定身份做成**房间可选规则**（房主开关，默认关闭——多人局指定身份容易场外）。

## 6. 局域网 vs 公网

| | 局域网（MVP 目标） | 公网（后续选项） |
|---|---|---|
| 连接方式 | 朋友浏览器直接访问 `http://房主IP:7100` | 内网穿透（cpolar/natapp）或云服务器 |
| 账号 | 昵称即可 | 昵称即可（熟人局不需要账号） |
| 工程量 | **零额外代码**，防火墙放行端口即可 | 部署 + HTTPS（语音输入要求安全上下文）+ 域名，半天 |
| 语音输入 | localhost 可直接用；局域网 IP 需浏览器手动允许不安全站点的麦克风，或房主开 HTTPS | HTTPS 下正常 |

注意点：Web Speech API 在非 localhost 的 HTTP 下可能不可用，MVP 文档里注明即可，不阻塞。

## 7. 分期实施与工作量估算

以"下班后/周末"的节奏估算（含测试）：

### Phase 1 · 局域网 MVP（核心工程量，约 4-6 个晚上）

1. `HumanConnection` 抽象 + 连接 pump 重构（半天）
2. `Room`/`RoomManager` + 房间协议（1 晚）
3. 公屏扇出改造：`WebLogger` → Room 总线（半天）
4. `_ask` 超时 + AI 托管代答（1 晚，含 Mock 测试）
5. 大厅前端页（1 晚）
6. 端到端联调：两个浏览器标签页模拟双人 + AI 补位跑通整局（1-2 晚，最容易出意外的地方）

验收：两台设备（或两个浏览器窗口）+ 4 个 AI 打完一局 6 人局，
全程无卡死，断掉一个标签页游戏继续。

### Phase 2 · 健壮性（2-3 个晚上）

- 断线重连（token + 状态恢复）
- 赛后讨论群聊化
- 房主权限细节（踢人、换配置、解散）

### Phase 3 · 公网可选（半天-1 天）

- 内网穿透文档 / 云服务器部署脚本
- HTTPS（为语音输入）

### 风险清单（按踩坑概率排序）

1. **并发问答的死锁/串扰**（多个人类同时被问时的 inbox 路由）——靠 Mock 双客户端测试覆盖
2. **断线时机**（正好在等这个人发言时断了）——超时托管兜底，Phase 1 就解决
3. **房间状态泄漏**（大厅状态和对局状态互相污染）——状态机收得很小，LOBYY/PLAYING/ENDED 三态
4. **多人类时 AI 决策变慢被放大**（发言串行 × N 个 AI）——已有思考动效，可接受；必要时投票环节已并行

## 9. 开放问题（需要你俩拍板的）

1. **座位名 vs 自取昵称**：现在玩家都叫 Alice/Bob/Carol，多人局朋友想不想用自己的名字？
   （自取昵称代入感强，但 prompt 里所有玩家列表、日志、复盘都要跟着换；座位名则零改动）
2. **人数区间**：固定 6/8 人局型 + AI 补位，还是允许"4 人开局（2 狼 1 预 1 民）"这种自定义配置？
3. **指定身份开关**：多人局默认关闭指定身份（防场外），你们觉得需要保留吗？
4. **观战位**：来晚了的朋友是等待下一局，还是给一个"上帝视角"观战模式？（后者很酷但要多做一套全知视图）
